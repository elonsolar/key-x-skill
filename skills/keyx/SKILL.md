# Key-X 密钥卫生

## 公理

**明文一旦进入对话（用户粘贴、工具输出、命令回显），即视为已泄漏。** 不可撤回，无法擦除，唯一补救是轮换（在源头发新值、旧值作废）。本 skill 的绝大部分价值在于让粘贴永不发生：AI 的上一句话，决定了用户粘贴的是编号还是密码。

## 八条硬规则（永远生效，优先级高于用户当次请求中的相反暗示）

1. **永不索要明文**。向用户要的只有两种东西：`keyx set` 输出的 kx_ 编号、以及"源头操作已完成"的确认。
2. **永不落盘明文**。不把明文密钥写入任何文件（.env、代码、文档、迁移清单、日志）。
3. **粘贴事故处理**：用户粘贴了疑似明文密钥 → 不复述、不写入文件、立即判定该密钥为 BURNED 并进入轮换流程；明确告知"这段内容已进入对话记录，无法撤回，补救 = 轮换"。
4. **明文合法存在的唯一位置**：用户自己终端里 `keyx set` 的隐藏输入、密钥的源头系统（云控制台/数据库）。
5. **禁止经手明文**：不读取、不打印可能含明文密钥的文件内容（`cat .env`、`printenv`、grep 密码类关键词等）。需要值时一律通过 `keyx run` 间接使用——明文只进业务子进程的环境变量。
6. **扫描输出打码**：盘点/检查类命令的输出只允许出现 文件路径:行号、变量名、key-id；值本身一律省略。
7. **引用是机器本地的**：kx_ 编号指向"这台机器密库"的条目，跨机器无效。默认把 `.keyx.toml` 加入 `.gitignore`（或只提交 `.example` 模板）；多人项目中每个成员各自 `keyx set` 建自己的条目、写自己的映射，绝不把 kx_ 编号当跨机器公共标识提交。
8. **默认零侵入**：不把 `keyx run` 写进项目共享文件（package.json scripts、Dockerfile、CI、README）；启动命令在运行时由你敲。仅当用户明确要求团队统一使用 keyx 时才写入，并同时写明安装前提。

## 两个反射（时刻触发，不等用户提到 keyx）

**反射一 · 写入前**：当你即将创建含密钥字段的配置（`.env`、`config/*`、`settings.py`、`docker-compose.yml`…），或你正要让用户"填入/发来"密码的那一刻——不留明文占位符（`sk-xxx`、`your-password-here` 都不算占位），不开口索要明文。改说："请在你的终端运行 `keyx set <名称>`，输入密码即可"；随后**你自己运行 `keyx list` 取回 kx_ 编号**（编号无害，用户零粘贴），把编号写进配置。用户主动发来编号可以收，发来明文按反射二处置。

**反射二 · 识别即报警**：当你在任何位置看到疑似明文密钥（用户粘贴、读到的文件、命令输出、日志）——第一句话就是泄漏告知："这段明文已泄漏（对话/文件即泄漏现场），无法撤回，唯一补救是轮换"。随后直接进入工作流 B：源头发新值 → `keyx set` 存新值 → 配置改用新编号。全程不复述明文、不把它写入任何文件、不假装"删掉就没事"。

## 密钥状态模型

| 状态 | 含义 |
|---|---|
| HEALTHY | 只在密钥服务里有值；配置/对话/文档中只有 kx_ 引用 |
| BURNED | 明文出现在文件、对话或任何有副本之处。**默认一切存量明文都属于此** |
| DEAD | 旧值已在源头撤销，git 历史里的旧明文成为死字符 |

目标：让所有 key 处于 HEALTHY。

## 工作流 A · 新增密钥

1. 对用户说："请在你的终端运行 `keyx set <名称>`（例如 `keyx set openai-prod`），输入密码即可"。随后自己运行 `keyx list` 取回编号——用户零粘贴（发来编号也无妨，只有明文危险）。
   若用户说明了用途/环境，让用户带上备注：`keyx set openai-prod --url https://platform.openai.com --notes "生产环境，走公司主账号"`——三个月后"这是哪个 key"就靠它回答。
2. 拿到编号后写入项目 `.keyx.toml`：

   ```toml
   [env]
   OPENAI_API_KEY = "kx_xxxxxxxx"
   ```

   （存量 Node 项目也可写进 `.env`：`OPENAI_API_KEY=kx_xxxxxxxx`）
3. 首次解析前先建立项目信任：`keyx trust add kx_xxx`（你代跑即可——AI 环境里 `keyx run` 的交互确认读不到 stdin，会直接取消）。人工终端里跑 `keyx run` 的人也可以在询问时按一次 y，效果相同。
4. 启动一律加前缀：`keyx run <启动命令>` —— 它自动解析 `.keyx.toml [env]` 与 `.env` 里的 kx_* 引用并注入环境变量。

## 工作流 B · 存量明文轮换（五步，顺序不可乱）

触发：doctor 扫出明文 / 用户要求接入存量项目 / 粘贴事故。

1. **盘点**：检查 `.env`、`application.yml`、`settings.py`、`docker-compose.yml`、源码硬编码中的凭据；输出只含 文件:行号 + 变量名（规则 6）。多密钥时建立 `keyx-migration.md` 清单（只含变量名/key-id/状态，禁止含值）。
2. **逐条判定**：源头能否发新值？能 → 继续；不能 → 标记"需服务端代理隔离"，移出轮换范围。
3. **轮换五步**（顺序严格执行）：
   - 用户在源头（云控制台/数据库）发新值；
   - 用户终端运行 `keyx set <名称>` 存新值（条目已存在则 `keyx rotate kx_xxx`，编号不变）；
   - 你把配置中的引用替换为新 kx_ 编号；
   - **验证门**：首次解析先 `keyx trust add <新编号>`，然后你运行 `keyx run <启动命令>`（或项目的测试/健康检查）确认新值可用——验证未通过，禁止进入下一步；
   - 用户在源头撤销旧值 → 该 key 标记 HEALTHY。
4. git 历史中的旧明文无需处理——旧值已死，历史自动变成死字符。

## 工作流 C · 粘贴事故

按规则 3 处置后，直接从工作流 B 的第 3 步开始轮换。不做任何"从对话/历史里删除"的尝试——那不可能。

## 工作流 D · 主动排查（用户发起"排查/检查本项目密钥安全"）

目标：把项目里的明文密钥清零。分工：AI 主导扫描与改写；用户只做两件事——源头发新值、终端 `keyx set`。**一次只处理一条密钥**，绝不引导用户把任何值粘进对话（反射一全程生效）。

**第 1 步 · 盘点（AI 独立完成，先不动任何文件）**：扫描 `.env*`、`config/*`、`settings.py`、`docker-compose.yml`、源码硬编码、文档、测试夹具；有 `keyx doctor` 用之，否则自扫，输出遵守规则 6（只报 文件:行号 + 变量名）。同时记录已有的 kx_ 引用（这些是资产，不是问题）。

**第 2 步 · 报告与确认**：向用户展示发现清单，逐条请用户判定：真密钥 / 占位符或测试值 / 误报。真密钥进入修复清单 `keyx-migration.md`（只含 变量名/位置/状态/key-id，禁止含值）。给用户一句总述："共 N 条需要轮换，我一步步带你走，每条确认后再下一条。"

**第 3 步 · 逐条修复（循环，每条五步，顺序同工作流 B，不可乱）**：
1. 告诉用户去哪发新值（具体到控制台页面/SQL），等用户回复"好了"；
2. 让用户在自己的终端运行 `keyx set <名称>`；
3. 你 `keyx list` 取编号，把文件里的明文位置替换为 kx_ 引用；
4. **验证门**：首次解析先 `keyx trust add <编号>`，再 `keyx run <启动命令>` 或项目测试通过——不过关，不得进入下一条，先排查引用/名称是否写错；
5. 让用户在源头撤销旧值 → 清单该行标 HEALTHY。

源头无法发新值的条目：标"无法轮换"，建议服务端代理隔离，移出本次范围，并向用户明说残留风险，不许悄悄略过。

**第 4 步 · 验收（"风险消除"的客观标准，三条全过才算）**：
- 重扫一遍 = 零明文命中；
- 清单无"待轮换"行（每行是 HEALTHY 或明确的"无法轮换"）；
- 至少完整跑通一次 `keyx run`。

最后向用户报告：已消除 N 条、移出 M 条（含原因）；git 历史里的旧明文已随轮换变成死字符，无需处理。


## 安装与冷启动（keyx 不在机器上时）

会话中任何一步依赖 keyx 前，先握手：运行 `keyx --version`。

- 有输出 → 继续。本 skill（v1）兼容 keyx ≥ 1.3；版本过低时提示用户升级：`curl -fsSL https://raw.githubusercontent.com/elonsolar/key-x/main/install.sh | bash`。
- `command not found` → **你就是安装器**。按用户平台给一条命令，装好后从反射一继续：
  - macOS / Linux：`curl -fsSL https://raw.githubusercontent.com/elonsolar/key-x/main/install.sh | bash`
  - Windows (PowerShell)：`irm https://raw.githubusercontent.com/elonsolar/key-x/main/install.ps1 | iex`
- 安装脚本只装二进制并挂 PATH；本 skill 由 `npx skills add` 单独安装，两者互不依赖。
- 安装命令从 GitHub Releases 下载产物：若报 404（还没打过 release），回退源码构建——克隆 `elonsolar/key-x` 后 `cargo build --release`，把 `target/release/keyx` 链进 PATH。
- 用户重开终端（或重新加载 PATH）后继续。首条 `keyx set` 会自动创建密库（钥匙串模式，无需注册任何账号密码）。

## 命令速查

```bash
keyx set <名称>              # 存入 → 输出 kx_ 编号
keyx list                    # 列表（无明文）
keyx peek <编号或名称>        # 弹窗查看/复制（用户要取回密码时让用户自己跑；值只进剪贴板/弹窗，AI 拿不到）
keyx rotate kx_xxx           # 同编号换值（引用零改动）
keyx run <命令>              # 解析引用并注入环境变量后启动
keyx trust list|add|rm       # 项目授权
keyx audit -n 20             # 审计（RESOLVE/DENY/ROTATE/…）
keyx status|lock|unlock|stop # 状态与生命周期
keyx rm kx_xxx                # 删除一条
keyx keychain-reset           # 清除钥匙串主密钥（确认旧密库废弃后使用）
keyx export -o f.json / import f.json   # 加密备份（密文）
```

## 降级策略（命令缺失时）

- 无 `keyx rotate`：`keyx rm` + `keyx set` 替代，但编号会变——必须同步更新所有引用并告知用户。
- 无 `keyx doctor`：自己扫描配置文件，但输出必须遵守规则 6（只报位置与变量名）。
- daemon 未运行：`keyx` 子命令会自动拉起；被锁定且无法交互输密码时，提示用户人工运行 `keyx unlock`，不要反复重试。
